# 개인 문서 허브 프로토콜

## 차례

1. 자리 판정
2. 프로필과 재정 문서
3. 파일과 디렉터리 분리
4. 파일명과 README
5. frontmatter
6. 근거가 필요한 경우
7. 현행 문서와 시점 기록

10. 이동과 보관
11. 검증

## 자리 판정

입력 조각마다 다음 순서로 판단한다.

1. **개인의 비교적 안정적인 특성인가** → `my-profile/`의 경력, 업무 방식, 개인적 배경 문서
2. **개인의 목표와 계속 바뀌는 계획인가** → 해당 프로필 주제의 현행 계획 문서
3. **특정 시점의 금액·상태·보유 목록인가** → 기준월 또는 기준일이 붙은 snapshot
4. **여러 프로젝트에서 다시 쓸 원칙·노하우인가** → 허브의 해당 지식 주제
5. **프로젝트 하나의 기획·설계·운영 사실인가** → 해당 프로젝트 저장소
6. **원문이나 대화의 시점 기록인가** → 원문을 보존하고, 허브에는 필요한 조각의 출처만 남김

어느 자리에도 맞지 않으면 가까운 곳에 밀어 넣지 않는다. 첫 실제 문서가 생길 때 새 자리를 제안한다.

## 프로필과 재정 문서

기본 프로필은 다음 역할을 분리한다. 실제 내용이 있을 때만 문서를 만든다.

```text
my-profile/
├── README.md
├── 001-career-and-work-style.md
├── 002-personal-context.md
└── finances/
    ├── 001-financial-plan.md
    ├── 002-financial-snapshot-YYYY-MM.md
    ├── 003-stock-investing.md
    ├── 004-retirement-fund-plan.md
    └── 005-housing-relocation.md
```

- `001-career-and-work-style.md`: 경력, 가치관, 공통 업무 성향
- `002-personal-context.md`: 프로젝트 우선순위에 영향을 주는 개인 배경. 식별 정보는 제외
- `001-financial-plan.md`: 목표, 제약, 자금 운용 원칙과 확인할 질문
- `002-financial-snapshot-YYYY-MM.md`: 그 시점의 소득, 자산, 부채, 평가금과 기준일
- `003-stock-investing.md`: 투자 노하우, 판단 기준, 전략별 유지·중단 조건
- `004-retirement-fund-plan.md`: 퇴직금의 목적, 계좌 안 자산 배분과 변경 조건
- `005-housing-relocation.md`: 이전 목표, 후보, 자금 차이와 실행 순서

금액과 종목 비중은 snapshot이 정본이다. 계획 문서에 같은 수치를 반복하지 않는다. snapshot의 실제 관측일을 모르면 그 사실을 명시하고 현재 값처럼 쓰지 않는다.

새 snapshot은 `assets/financial-snapshot-template.md`를 사용한다. 실제로 확인되지 않은 절은 빈칸이나 추정값으로 채우지 않고 제거하거나 `확인 필요`에 기록한다. 계좌번호, 로그인 정보와 API 자격증명은 snapshot에 기록하지 않는다.

## 파일과 디렉터리 분리

주제는 파일 하나로 시작한다. 다음 조건을 모두 충족하면 디렉터리로 분리한다.

1. 같은 주제에 독립적으로 갱신할 문서가 세 편 이상이다.
2. 각 문서가 서로 다른 질문에 답한다.
3. 각 문서가 독립적으로 바뀌어도 나머지 문서가 곧바로 낡지 않는다.

세 편 미만이어도 독자나 공개 대상이 다르면 분리할 수 있다. 반대로 다음 경우에는 세 편 이상이어도 한 문서를 유지한다.

- 같은 표나 닫힌 목록을 임의로 나눈 것
- 한 결정 체계의 앞뒤 근거가 강하게 연결된 것
- 분리하면 같은 사실을 여러 파일에서 반복해야 하는 것

## 파일명과 README

- 경로는 소문자 영문 kebab-case를 기본으로 하고 본문은 한국어로 쓴다.
- 본문 산문에는 고정 폭 하드 래핑을 사용하지 않는다. 한 문단은 한 줄로 쓰며, 의미 단락과 Markdown 구조를 보존하기 위한 줄바꿈만 사용한다.
- `my-profile/`의 일반 문서는 각 디렉터리 안에서 읽는 역할을 나타내는 3자리 접두사 (`001-`, `002-`)를 붙인다. 번호는 생성 순서가 아니라 문서 역할의 순서이므로 기존 문서 사이에 새 파일이 생겼다는 이유만으로 모두 다시 번호 매기지 않는다.
- 같은 역할의 시점 기록은 같은 번호를 공유한다. 예를 들어 모든 재정 snapshot은 `002-financial-snapshot-YYYY-MM.md`로 이름을 붙여 새 snapshot이 생겨도 다른 문서의 번호와 링크가 바뀌지 않게 한다.
- `README.md`는 진입점 이름이므로 숫자 접두사를 붙이지 않는다. 이 접두사 규칙을 다른 최상위 주제에 자동으로 확대하지 않고, 해당 주제의 읽기 순서가 실제로 필요할 때 별도로 정한다.
- 공백, `final`, `new`, `latest`, 버전 의미가 불명확한 `v2`를 사용하지 않는다.
- 시점 기록은 `NNN-주제-snapshot-YYYY-MM.md` 또는 `NNN-YYYY-MM-DD-주제.md`로 기준일을 드러낸다.
- 허브 루트와 독자가 직접 들어오는 최상위 주제는 `README.md`를 기본 진입점으로 사용한다.
- 상위 README가 하위 문서를 직접 나열하고 관리 원칙까지 설명할 수 있으면 하위 디렉터리에는 README를 만들지 않는다.
- 하위 README는 그 디렉터리를 독립적으로 탐색하거나, 문서 목록과 고유 규칙을 상위에 두면 상위 README가 깊어지는 경우에만 만든다.
- README에서 다른 README를 거쳐야 실제 문서에 도달하는 연결 사슬을 만들지 않는다.
- README에는 목적, 먼저 읽을 순서, 필요한 문서 링크와 그 자리만의 관리 원칙만 둔다.
- 파일 수처럼 곧 낡는 숫자를 README에 적지 않는다.

### README 템플릿 승격

- 현재 `my-profile/README.md`는 프로필 진입점의 첫 사례이지 범용 허브 템플릿이 아니다.
- 서로 다른 최상위 주제 README가 두 종류 이상 생기면 목적, 읽는 순서, 공개 경계처럼 반복되는 절을 비교한다.
- 두 종류 이상에서 실제로 공통인 절만 `assets/`의 README 템플릿으로 승격한다.
- 특정 주제에만 필요한 절은 템플릿의 필수 항목으로 만들지 않는다.
- 템플릿을 만들기 전에도 현재 README는 직접 갱신한다. 템플릿이 없다는 이유로 문서 작업을 미루지 않는다.

## frontmatter

모든 허브 문서에 필드를 기계적으로 늘리지 않는다. AI가 만들거나 크게 재구성해 사용자 검토가 필요한 문서는 다음 상태 필드만 기본으로 사용한다.

```yaml
---
status: proposed
---
```

허용 상태:

- `proposed`: AI가 작성·재구성했고 사용자 내용 검토가 남음
- `approved`: 사용자가 내용과 사용 범위를 승인함
- `archived`: 현행 문서가 아니며 대체 또는 종료 이유가 있음

`my-profile/` 아래 문서는 별도 frontmatter가 없어도 기본 비공개다. 공개 여부는 frontmatter 속성으로 관리하지 않는다. AI는 기본 비공개 문서의 내용을 공개·무관 문서에 복사하지 않는다. 공개 자료가 필요하면 공개 목적과 대상 문서를 먼저 확인하고 필요한 내용만 별도 문서로 추출한 뒤 사용자의 명시적 승인을 받는다. 내부 계획에서 필요할 때도 상세 개인정보를 반복하지 않고 정본을 링크한다. 실제 보호는 저장소와 파일 접근권한으로 구현한다.

일반 문서와 README에는 `updated`를 두지 않는다. Git 저장소라면 수정 이력은 Git에서 확인하고, 사람이 매번 동기화해야 하는 중복 메타데이터를 만들지 않는다. 아직 Git 저장소가 아니면 파일 mtime을 문서의 의미 있는 기준일로 간주하지 않고, 변경 이력이 필요할 때 저장소 전환을 별도 결정한다. snapshot처럼 날짜가 문서 내용의 일부일 때만 `snapshot-date: YYYY-MM-DD` 또는 `snapshot-month: YYYY-MM`을 추가한다. frontmatter 값은 스칼라만 사용하고, 출처와 관련 문서 링크는 본문에 둔다.

## 근거가 필요한 경우

- 사용자 자신의 프로필, 목표와 계획에는 `기록 범위와 출처` 절을 자동으로 만들지 않는다.
- 새 허브로 옮긴 날짜, AI가 분리한 과정과 이전 파일 경로를 현행 문서 본문에 남기지 않는다.
- 외부 조사, 인용, 측정값처럼 나중에 근거를 다시 확인해야 할 때만 해당 주장 가까이에 출처를 둔다.
- 수치에는 의미 있는 관측 기준일을 붙인다. 기준일이 없으면 `[확인 필요]`로 표시한다.
- 원문에 없는 의도, 결론, 담당자와 날짜를 만들지 않는다.
- AI의 제안은 사실이나 사용자 결정처럼 쓰지 않고 `권고`임을 밝힌다.
- 외부 원본을 직접 수정·이동·삭제하려면 사용자 요청 범위에 포함되어 있어야 한다.
- 로컬 출처가 꼭 필요하면 저장소 이름과 저장소 상대경로로 적는다. 사용자명, 홈 디렉터리와 작업공간 루트를 포함한 머신 절대경로는 문서에 남기지 않는다.
- 스킬 예시와 명령에는 실제 머신 경로 대신 `<workspace-root>`, `<hub>`, `<repository>` 같은 자리표시자를 쓴다.

## 현행 문서와 시점 기록

| 부류 | 예 | 갱신 방식 |
| --- | --- | --- |
| 현행 문서 | 프로필, 원칙, 계획, 프로젝트 지도 | 같은 질문에 답하는 기존 절을 갱신 |
| 시점 기록 | 재정 snapshot, 당시 조사, 대화 원문 | 과거 본문을 현재 값으로 덮지 않고 새 기록 생성 |

계획이 바뀌었다는 이유만으로 snapshot을 고치지 않는다. 반대로 현재 계획을 새 날짜 파일로 계속 복제하지 않는다. 파일이 언제 바뀌었는지는 Git이 갖고, 결정이 바뀐 이유는 현행 문서에 남긴다.

## 정본과 링크

- 같은 사실을 두 문서에 반복해야 하면 정본 하나를 지정하고 다른 문서는 링크한다.
- 프로젝트 코드와 함께 바뀌는 사실은 프로젝트 저장소가 정본이다.
- 개인 공통 목표와 승인된 업무 성향은 문서 허브가 정본이다.
- 문서 이동·이름 변경 시 `rg`로 이전 경로와 파일명을 검색한다.
- 상대 링크는 대상 파일이 실제로 존재하는지 확인한다.
- 링크 표시문과 설명은 문서를 읽지 않고도 목적을 알 수 있게 쓴다.

## 공개 경계

`my-profile/` 전체와 다음 내용은 별도 표기 없이 기본 비공개다.

- 상세 주소와 가족 식별 정보
- 계좌번호, 증권사 로그인 정보, API 키와 토큰
- 현재 자산·부채·소득의 상세 수치
- 공개되지 않은 사업 계획과 개인 일정

공개 문서를 만들 때 기본 비공개 문서를 그대로 승격하지 않는다. 공개 목적과 대상 문서를 확인하고 필요한 내용만 별도 문서로 추출한 뒤 사용자의 명시적 승인을 받는다. GitHub 프로필과 개인 웹사이트에도 승인된 별도 공개 문서만 사용한다.

## 이동과 보관

원본을 허브로 옮길 때는 다음 순서를 지킨다.

1. 원본과 들어오는 참조를 검색한다.
2. 내용을 역할별 허브 문서에 배치한다.
3. 누락과 중복 정본을 확인한다.
4. 현행 참조를 새 정본 또는 프로젝트 내부 정본으로 바꾼다.
5. 사용자가 이동을 요청한 경우에만 원본을 제거한다.
6. 과거 로그의 본문은 당시 경로를 담은 시점 기록이므로 고치지 않는다.

사용자가 변환 후 원문 삭제를 허용했더라도 대상 현행 문서가 `proposed`인 동안에는 삭제하지 않는다. 사용자가 변환 결과를 검토해 삭제 시점을 승인한 뒤, 들어오는 링크와 누락을 확인하고 원문을 삭제한다. 이 경우 삭제 예정 원문을 보존하기 위한 `sources/`나 `archive/`를 새로 만들지 않는다.

보관은 대체 문서나 종료 이유가 있을 때만 한다. 보관 문서에는 `status: archived`, 보관일, 이유와 대체 문서 링크를 남긴다.

## 검증

허브 문서를 고친 뒤 작업 범위에 맞게 확인한다.

```bash
find <hub> -type f -empty -print
find <hub> -type d -empty -print
rg -n '<이전-경로|이전-파일명>' <hub> <관련-프로젝트>
git diff --check
git status --short
git diff --name-only
```

- `find` 결과가 의도하지 않은 빈 문서·디렉터리를 가리키면 제거하거나 내용을 채운다.
- 이전 경로 검색은 과거 로그와 archive를 현행 오류로 취급하지 않는다.
- Git 명령은 대상이 Git 저장소일 때만 실행한다.
- 최종적으로 새 문서의 모든 상대 링크를 열 수 있는지 확인한다.
