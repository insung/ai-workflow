# My Document Hub

개인 프로젝트에 흩어진 맥락을 필요한 근거와 공개 경계를 보존하면서 지속적으로 갱신할 수 있는 문서로 정리한다. 문서 수를 늘리는 것이 아니라, 나중에 같은 질문을 다시 받았을 때 정본을 찾을 수 있게 하는 것이 목적이다.

## 시작하기

1. 사용자가 허브 경로를 지정했으면 그 경로를 사용한다. 지정하지 않았으면 Codex가 현재 접근할 수 있는 작업공간과 현재 저장소의 형제 디렉터리에서 `my-document-hub`를 찾는다. 하나만 확인되면 사용하고, 없거나 둘 이상이면 사용자에게 묻는다.
2. 허브와 원본 저장소의 `AGENTS.md`, `README.md`, 관련 현행 문서를 존재하는 범위에서 읽는다.
3. 쓰기 전에 대상 경로의 기존 문서와 같은 질문에 답하는 문서를 검색한다.
4. 자리, 파일명, 상태, 공개 경계 또는 분리 여부를 판단할 때 [document-protocol.md](references/document-protocol.md)를 읽는다.
5. Markdown에 `tandem-comments` 블록이 있거나 사용자가 문서 코멘트를 언급하면 `code-comments` 스킬의 Obsidian workflow를 함께 적용한다. 확인한 열린 코멘트에는 한국어 답글을 남기고 `open` 상태를 유지한다. 코멘트 해결과 삭제는 사용자가 Obsidian에서 직접 처리한다.
6. 재정 현황 문서를 새로 만들 때는 [financial-snapshot-template.md](assets/financial-snapshot-template.md)를 복사해 실제로 확인된 절만 남긴다. 템플릿 자체에는 개인의 금액과 종목을 기록하지 않는다.
7. 프로필의 레이더 차트를 만들거나 갱신할 때는 [radar-assessments.md](references/radar-assessments.md)를 읽고, 새 질문지는 [radar-questionnaire-template.md](assets/radar-questionnaire-template.md)를 사용한다.

## 범위 지키기

- 기본 수정 범위는 문서 허브다. 외부 원본 저장소는 사용자가 이동·동기화·참조 정리를 요청한 경우에만 수정한다.
- 원본 이동은 새 문서 생성과 검증, 들어오는 참조 수정이 끝난 뒤 수행한다.
- 프로젝트 하나에만 적용되는 실행 지시, 코드 사실과 운영 절차는 해당 프로젝트가 정본을 갖는다. 허브에는 여러 프로젝트에서 재사용할 개인 맥락, 원칙, 계획과 결정만 둔다.
- 기존 사용자 변경을 되돌리거나, 요청하지 않은 분류 체계를 한꺼번에 만들지 않는다.
- 내용 없는 문서, 빈 템플릿과 미래를 가정한 디렉터리를 만들지 않는다.
- 원문을 현행 문서로 분해한 뒤 삭제하도록 사용자가 허용했으면 별도 `sources/`를 만들지 않는다. 원문은 대상 문서가 사용자 검토를 통과할 때까지 유지하고, 검토가 끝난 뒤에만 삭제한다.
- 스킬과 허브 문서에 사용자명·홈 디렉터리·머신별 작업공간을 포함한 절대경로를 기록하지 않는다. 스킬 설명에는 `<workspace-root>` 같은 자리표시자를, 허브 문서의 출처에는 저장소 이름과 저장소 상대경로를 사용한다.

## 입력을 먼저 분해하기

한 입력을 한 파일로 가정하지 않는다. 다음 기준이 다르면 조각을 나눈 뒤 각각의 자리를 정한다.

- 답하는 질문
- 갱신 주기
- 독자와 공개 대상
- 정본이 되는 출처
- 현행 계획인지 시점 기록인지

분리한 조각은 [document-protocol.md](references/document-protocol.md)의 자리 판정 순서로 배치한다. 결정이 하나만 남으면 바로 제안하고, 서로 걸린 결정이 둘 이상이면 한 번에 하나씩 사용자에게 확인한다.

## 플랫 구조와 디렉터리

- 한 주제는 파일 하나로 시작한다.
- 허브 루트 바로 아래의 `GOAL.md` 같은 파일에는 숫자 접두사를 붙이지 않는다. 최상위 주제 디렉터리 아래의 문서와 asset에는 그 디렉터리 안의 역할·읽기 순서를 나타내는 3자리 접두사를 붙인다. `README.md`, 숨김 설정 파일과 사용자가 지정한 예외는 제외한다.
- 같은 주제에 **독립적으로 갱신할 문서가 세 편 이상** 생기면 주제 디렉터리로 분리한다.
- 줄 수만으로 문서를 나누지 않는다. 갱신 주기, 독자, 공개 대상, 정본이 갈리는지를 본다.
- `README.md`는 허브 루트나 최상위 주제처럼 독자가 탐색을 시작하는 자리에 둔다. 상위 README가 하위 문서를 충분히 설명하면 하위 디렉터리에 README를 반복해서 만들지 않는다.
- 하위 디렉터리를 독립적으로 열어 쓰거나, 상위 README가 상세 목록 때문에 깊어질 때만 하위 README를 만든다. README가 다른 README만 가리키는 연결 사슬은 만들지 않는다.
- README가 필요한 자리에는 `README.md` 하나만 사용하고 별도 `INDEX.md`, `안내.md`, `latest.md`를 만들지 않는다.
- 서로 다른 최상위 주제 README가 두 종류 이상 생기기 전에는 한 사례를 범용 템플릿으로 고정하지 않는다. 공통 절이 실제로 반복될 때만 템플릿으로 승격한다.

## 문서 상태와 공개 경계

AI가 새로 쓰거나 구조를 크게 바꾼 문서는 `status: proposed`로 시작한다. 사용자가 내용과 사용 범위를 확인하면 `approved`로 바꾼다. 더 이상 현행이 아니며 대체 문서나 종료 이유가 있으면 `archived`로 바꾼다. 열린 코멘트가 미확인 사실이나 결정을 다루면 `proposed`를 유지하되, 형식 질문이나 이미 답변된 코멘트가 있다는 이유만으로 승인을 막지는 않는다. `approved` 문서를 크게 재구성해 다시 내용 검토가 필요해지면 `proposed`로 되돌린다. 읽기 좋게 정리됐다는 사실만으로는 승인하지 않는다.

`my-profile/`은 별도 frontmatter가 없어도 기본 비공개다. AI는 이 내용을 사용자가 승인하지 않은 공개 문서나 무관한 프로젝트 문서에 복사하지 않는다. 공개 자료가 필요하면 목적과 대상 문서를 확인하고 필요한 내용만 별도 문서로 추출한 뒤 사용자의 명시적 승인을 받는다. 공개 여부를 frontmatter 속성으로 관리하지 않는다. 이 절차는 AI의 재사용 경계이며 파일 접근권한을 제공하는 보안 기능은 아니다.

`updated`는 일반 문서와 README의 기본 필드로 사용하지 않는다. Git 저장소라면 마지막 수정 이력은 Git에서 확인한다. 아직 Git 저장소가 아니라면 수동 `updated`를 대신 유지하지 말고, 변경 이력이 필요한지와 저장소 전환을 사용자와 별도로 결정한다. 문서 내용 자체에 기준일이 필요한 snapshot만 `snapshot-date` 또는 `snapshot-month`를 사용한다.

## 만들고 갱신하기

1. 기존 문서와 원본의 사실, 날짜, 결정, 미확인 사항을 구분한다.
2. 같은 질문에 답하는 현행 문서가 있으면 새 파일 대신 기존 절을 갱신한다.
3. 변하는 금액과 보유 현황은 날짜가 붙은 snapshot에 기록하고, 계획·원칙 문서에는 링크만 둔다. snapshot의 표와 파생값은 asset 템플릿의 필드명과 계산 기준을 따른다.
4. 중복되는 사실은 정본 하나를 정하고 다른 문서는 상대 링크로 연결한다.
5. 문서를 이동하거나 이름을 바꾸면 들어오는 링크와 문서를 직접 나열하는 가장 가까운 `README.md`를 같은 세션에 고친다.
6. AI가 추정으로 빈 내용을 채우지 않는다. 사용자가 나중에 제공하기로 한 내용은 확인할 범위로 짧게 남긴다.
7. 산문은 80자나 100자 같은 고정 글자 수에 맞춰 강제로 줄바꿈하지 않는다. 한 문단은 원문에서 한 줄로 유지하고, 문단·목록·표·인용·코드처럼 의미나 Markdown 구조가 바뀌는 지점에서만 줄을 바꾼다.
8. 기존 문서의 하드 래핑을 제거할 때는 같은 문단 안의 줄바꿈만 합치고 단어, 문장부호, 문단 순서와 의미를 바꾸지 않는다.
9. 레이더 평가는 프로필 본문의 현재 해석, `questionnaires/`의 반복 질문·평가 이력, `assets/`의 차트로 역할을 나눈다. 같은 측정 축이면 기존 차트를 갱신하고, 독립적인 새 측정 질문이 확인될 때만 새 차트를 제안한다.

## 검토와 검증

문서를 만들거나 고친 뒤 다음을 확인한다.

- 새 문서가 실제 질문 하나에 답하는가.
- `status`, 공개 승인과 대상, 기준일과 근거가 내용에 맞는가.
- 해결되지 않은 Tandem 코멘트를 누락하거나 코멘트 블록을 훼손하지 않았는가.
- 빈 문서·빈 디렉터리·깨진 상대 링크·중복 정본이 없는가.
- 이동한 원본 경로를 현행 문서가 계속 참조하지 않는가.
- Git 저장소라면 `git diff --check`, `git status --short`, `git diff --name-only`로 범위를 확인했는가.

완료 보고는 `완료 / 변경 문서 / 이동·삭제한 원본 / 검증 / proposed로 남은 내용 / 다음 검토`만 간결하게 적는다.
