# Commit Rule

커밋 메시지를 쓰기 전에 범위와 저장소의 실제 운영 방식을 확인한다. 규칙을 적용하기 어려우면 임의로 우회하지 않고 사용자에게 확인한다.

## 커밋 범위

### 1. 작업 루트와 저장소 확인

현재 디렉터리가 저장소면 그 저장소를 우선 대상으로 삼는다. 현재 작업이 형제 저장소도 수정했다면 그 형제까지 포함하는 가장 가까운 작업공간을 루트로 정한다. 작업과 무관한 상위 디렉터리나 사용자 홈 전체를 스캔하지 않는다.

루트 직계 하위에 여러 저장소가 있으면 다음처럼 확인한다. 실제 경로는 현재 작업공간에서 구하고 스킬이나 문서에 머신 절대경로를 기록하지 않는다.

```bash
for d in "$ROOT"/*/; do
  [ -d "$d/.git" ] && { echo "=== $d"; git -C "$d" status --short; }
done
```

실패하거나 접근할 수 없는 저장소는 `없음`이 아니라 `확인 불가`로 표시한다.

### 2. 커밋 전에 범위를 보여준다

| 저장소 | 미커밋 | 이번 세션 |
| --- | --- | --- |

- `이번 세션`은 이 대화에서 실제로 편집한 파일과 대조한다.
- 출처를 판정할 수 없는 변경은 `불명`으로 표시하고 자동으로 커밋하지 않는다.
- 사용자가 다른 변경까지 포함하라고 명시하지 않으면 이번 세션 변경만 담는다.
- 한 파일에 여러 세션 변경이 섞였으면 [scope.md](references/scope.md)를 읽는다.

### 3. 계획·승인·실행·재확인

1. 저장소별, 주제별 커밋으로 나누고 제목 초안을 함께 보여준다.
2. 한 번 승인받은 계획은 저장소마다 다시 묻지 않고 실행한다.
3. 커밋 요청은 푸시 권한을 포함하지 않는다. 푸시는 별도 요청이 있을 때만 한다.
4. 커밋 후 같은 범위를 다시 스캔하고 남은 변경을 보고한다.

재확인 전에는 `커밋 완료`라고 보고하지 않는다.

## 커밋 메시지

```text
<type>(<scope>): <한국어 요약>
```

| type | 뜻 | 릴리즈 노트 | 버전 영향 |
| --- | --- | --- | --- |
| `feat` | 기능 | 기능 | minor |
| `fix` | 버그 수정 | 버그 수정 | patch |
| `perf` | 성능 | 성능 | patch |
| `refactor` | 동작 변화 없는 구조 개선 | 제외 | 없음 |
| `docs` | 문서 | 제외 | 없음 |
| `test` | 테스트 | 제외 | 없음 |
| `build` | 빌드·의존성 | 제외 | 없음 |
| `ci` | 파이프라인 | 제외 | 없음 |
| `chore` | 유지보수 | 제외 | 없음 |
| `style` | 포맷 | 제외 | 없음 |

호환성이 깨지는 변경은 `type!`을 쓰고 푸터에 `BREAKING CHANGE:`를 적는다.

### scope

scope는 생략하지 않고 소문자 kebab-case로 쓴다.

1. `git log --pretty=%s | head -30`으로 최근 표기를 확인한다.
2. 같은 주제의 기존 scope가 있으면 그대로 사용한다.
3. 새 주제라면 기술 레이어나 저장소명이 아니라 사용자가 구별할 수 있는 기능·업무 주제를 쓴다.

`backend`, `frontend`, `common`, `document`처럼 너무 넓은 값은 피한다. scope 하나를 고를 수 없다면 커밋을 나눈다. 상세 예시는 [commit.md](references/commit.md)를 읽는다.

### 요약과 본문

- 요약은 한국어 명사형, 약 50자 이내, 마침표 없음.
- `feat: 추가`, `fix: 수정`처럼 type과 뜻이 겹치는 말로 끝내지 않음.
- 개수만 쓰지 않고 무엇이 달라졌는지 표시.
- 제목·본문·PR에 사람 이름을 쓰지 않고 역할이나 사건으로 표현.
- 본문은 선택 사항이며 diff로 알 수 없는 이유, 제약, 트레이드오프를 평어로 기록.
- `Co-authored-by:` 같은 표준 트레일러는 허용.

본문과 푸터 형식은 [commit.md](references/commit.md)를 읽는다.

## 브랜치와 머지

문서·스킬처럼 배포하지 않는 개인 저장소는 기본 브랜치 하나를 사용한다. 배포 저장소에서 브랜치를 만들거나 머지할 때만 [branch.md](references/branch.md)를 읽고 다음을 먼저 확인한다.

```bash
git branch -a
git log --all --decorate --oneline -30
```

- 저장소의 기존 통합 브랜치와 작업 브랜치 접두사를 우선한다.
- 새 배포 저장소는 기본적으로 `main`과 짧게 유지되는 `feature/`, `fix/`, `hotfix/`를 사용한다.
- 여러 환경을 위한 장기 통합 브랜치는 실제 배포 필요가 있을 때만 추가한다.
- 공유 브랜치를 rebase하거나 force push하지 않는다.
- 작업 브랜치 force push가 꼭 필요하면 `--force-with-lease`를 사용한다.
- 머지 방식은 저장소의 기존 규칙을 우선한다. 규칙이 없다면 판단 커밋을 보존하는 `--no-ff`를 기본으로 하며 squash 여부가 결과에 영향을 주면 사용자에게 확인한다.

## PR

PR 제목도 `<type>(<scope>): <한국어 요약>`을 사용한다. 본문은 저장소의 기존 템플릿을 우선하고, 없으면 다음 세 항목을 기본으로 한다.

```markdown
Closes #

## 변경 내용

## 바뀐 곳

| 파일·폴더 | 무엇이 |
| --- | --- |
```

- 이슈 번호를 모르면 추측하지 않는다.
- `유심히 볼 곳`, `확인`, `화면`, `머지 뒤 조치`는 실제 내용이 있을 때만 추가한다.
- `확인`에는 이번 세션에서 실제로 실행한 명령과 결과만 적는다.
- 산문은 평어, 목록과 표는 명사형으로 쓴다.
- release-drafter가 있으면 설정에 선언된 label을 그대로 사용한다.
- 본문 초안을 사용자에게 보여주고 승인받은 뒤 `gh pr create`를 실행한다.

본문 상세는 [pr.md](references/pr.md)를 읽는다. 사용자가 이슈 생성을 요청했거나 PR이 닫을 이슈가 없을 때만 [issue.md](references/issue.md)를 읽는다.

## 이슈

- 기능과 버그 모두 목표와 검증 가능한 달성 조건을 쓴다.
- 버그는 확인된 재현 절차와 환경만 기록하고 빈 정보를 추측하지 않는다.
- 기존 이슈와 중복되는지 먼저 확인한다.
- 제목은 커밋과 같은 형식을 사용한다.
- 초안을 보여주고 승인받은 뒤 `gh issue create`를 실행한다.

## 태그와 릴리즈

배포 방식과 태그 이름은 저장소마다 다르므로 기존 workflow, 문서와 최근 태그를 먼저 확인한다.

```bash
git tag --sort=-creatordate | head -10
git log --first-parent --pretty=format:'%s' <이전-태그>..<현재-태그>
```

- 검증된 커밋에만 배포 태그를 붙인다.
- `BREAKING CHANGE`는 major, `feat`는 minor, `fix`와 `perf`는 patch 후보로 본다.
- 실제 버전 정책과 자동화가 다르면 저장소 규칙을 따른다.
- hotfix는 현재 배포 지점에서 분기하고 배포 뒤 기본·통합 브랜치에도 반영한다.

## 금지 사항

- 범위 스캔 없이 커밋 시작
- 다른 세션의 변경이나 출처 불명 변경을 승인 없이 포함
- scope 없는 커밋
- 승인 없는 PR·이슈 생성
- 요청 없는 push·tag·release
- 실행하지 않은 검증을 PR에 기록
- 이슈 번호, 배포 방식, 브랜치 체계 추측
- 공유 브랜치 rebase 또는 force push
- 사용자명·홈 디렉터리·머신 작업공간의 절대경로를 스킬과 저장소 문서에 기록
