# PR 본문 상세

`SKILL.md`의 「PR 만들기」 절에 이어, 본문 전문과 자리별 작성 기준을 정리한다.

## 문체

본문은 **존댓말도 반말도 쓰지 않는다.** 커밋 본문과 같은 문어체다. 이슈 본문에도 같은 규칙이 걸린다.

PR과 이슈는 사람에게 말을 거는 자리가 아니라 저장소에 남는 기록이다. 「~합니다」는 읽는 사람이 그 자리에 정해져 있다는 뜻이라 몇 달 뒤 제3자가 이력을 훑을 때 어색해지고, 「~해」는 릴리즈 노트로 나가는 문서의 격이 아니다.

| 자리 | 종결 | 예 |
| --- | --- | --- |
| 제목 | 명사형 | `feat(app-ranking): 기간을 주 단위로 선택` |
| 산문 문단 | 평어 `~다` | 재실행하면 같은 날짜가 중복 적재된다 |
| 목록 항목·표 칸 | 명사형 | `- 마이그레이션 : 없음` |
| 달성 조건 체크박스 | 명사형 | `- [ ] 앱 상세에서 기간을 주 단위로 선택 가능` |

| 고치기 전 | 고친 뒤 |
| --- | --- |
| 중복 적재되는 문제를 수정했습니다 | 재실행 시 같은 날짜가 중복 적재되던 것을 막는다 |
| 테스트는 전부 통과했어요 | 실행 : `pnpm test` · 결과 : 24개 통과 |
| 확인 부탁드립니다 | (쓰지 않는다. 리뷰 요청은 PR을 여는 행위 자체다) |
| 이 부분 좀 봐줘 | 캐시 만료 시각 계산을 유심히 볼 것 |

**템플릿에 남는 HTML 주석도 같다.** `<!-- ~해 주세요 -->`가 아니라 `<!-- ~를 적는다 -->`로 쓴다.

**사용자가 준 문장을 그대로 옮길 때만 예외다.** 인용부호로 감싸고 원문을 보존한다 — 고쳐 쓰면 무엇을 그대로 옮긴 것인지 알 수 없게 된다.

## 늘 쓰는 세 자리

`Closes #`·변경 내용·바뀐 곳만 있는 PR이 정상이다. 아래로 이어지는 자리는 쓸 내용이 있을 때만 만든다.

```markdown
Closes #

## 변경 내용

<!-- 이 PR이 무엇을 하는지 세 문장 이내 -->

## 바뀐 곳

| 파일·폴더 | 무엇이 |
| --- | --- |
|  |  |
```

## 쓸 내용이 있을 때만 만드는 자리

| 절 | 만드는 조건 | 없으면 어떻게 읽히는가 |
| --- | --- | --- |
| `## 유심히 볼 곳` | 일부러 그렇게 둔 선택이나 임시로 남긴 것이 있을 때 | 특별히 볼 곳이 없다 |
| `## 확인` | 이 세션에서 명령을 실제로 실행했을 때 | **아무것도 실행하지 않았다** |
| `## 화면` | 화면이 바뀔 때 | 화면이 바뀌지 않는다 |
| `## 머지 뒤 조치` | 환경변수·마이그레이션·배포 순서·되돌리기에 걸리는 것이 있을 때 | 머지하면 끝이다 |

**「없음」으로 채우지 않고 절을 통째로 지운다.** 빈 절이 넷 붙어 있으면 읽는 사람이 본문 전체를 건너뛴다.

```markdown
## 유심히 볼 곳

## 확인

- 실행 : `pnpm test packages/ui/src/chart`
- 결과 : 24개 통과

## 화면

| 전 | 후 |
| --- | --- |
|  |  |

## 머지 뒤 조치

```

## 「바뀐 곳」 표

**파일 이름이 아니라 그 파일이 왜 바뀌었는지를 적는다.** 파일 목록 자체는 GitHub의 Files changed 탭이 이미 보여준다.

```markdown
| 파일·폴더 | 무엇이 |
| --- | --- |
| `src/chart/axis.ts` | 축 눈금 계산을 주 단위까지 다룸 |
| `src/chart/__tests__/` | 주 단위 눈금 케이스 추가 |
| `pnpm-lock.yaml` | 의존성 갱신 |
```

- **파일이 많으면 폴더로 묶는다.** 한 폴더 안에서 같은 이유로 바뀐 파일은 폴더 한 줄이다.
- **한 줄은 30자 이내로 쓴다.** 넘으면 그 설명은 「변경 내용」이나 「유심히 볼 곳」으로 갈 내용이다.
- **자동 생성 파일은 한 줄로 묶는다.** lock 파일, 빌드 산출물, 포맷만 바뀐 파일이 여기 해당한다.
- 표가 열 줄을 넘으면 파일 단위를 폴더 단위로 한 단계 올린다.

## 「확인」 절

리뷰어가 이 자리를 읽고 하려는 일은 **자기 손으로 같은 확인을 다시 하는 것**이다. 그래서 명령을 그대로 옮겨 적는다.

```markdown
## 확인

- 실행 : `pnpm test packages/ui/src/chart`
- 결과 : 24개 통과
```

**이 세션에서 실행하지 않은 것을 적지 않는다.** 실행한 것이 없으면 이 절을 만들지 않고, 대화에서 사용자에게 알린다.

> 이 저장소에 테스트가 없어 아무것도 실행하지 못했습니다. PR 본문에 확인 절을 넣지 않았습니다.

## 「머지 뒤 조치」를 diff에서 찾는 방법

| 무엇을 찾는가 | 어디를 보는가 |
| --- | --- |
| 환경변수 | `.env.example` · `.env.sample` 변경, 코드에 새로 등장한 `process.env.*` · `os.environ[*]` |
| 마이그레이션 | `migrations/` · `alembic/` · `prisma/migrations/` 아래 새 파일 |
| 배포 순서 | 다른 저장소의 API 응답 형식에 맞춘 변경 — 두 저장소가 함께 나가야 한다 |
| 되돌리기 | 되돌릴 수 없는 변경(데이터 삭제, 형식 변환)이 있으면 그 변경을 적는다 |

위 경로를 실제로 확인했고 걸리는 것이 없으면 이 절을 만들지 않는다.

## 배포 PR 본문

통합 브랜치에서 배포 브랜치로 올리는 PR이다. 개별 변경 설명 대신 **이번에 무엇이 함께 나가는가**를 적는다.

```markdown
## 배포 목적

## 포함된 변경

<!-- git log --first-parent <이전 배포 지점>..<이번 지점> --pretty='- %s' 로 뽑는다 -->

### ✨ 기능
### 🐛 버그 수정
### ⚡ 성능

## 배포 시 유의사항

## 되돌리기
```

분류는 `SKILL.md`의 type 표를 따른다. `refactor`·`docs`·`chore`·`style`·`test`·`build`·`ci`는 릴리즈 노트에서 빠지므로 이 본문에도 넣지 않는다. 빈 분류는 지운다.

## 저장소에 이미 PR 템플릿 파일이 있을 때

`.github/PULL_REQUEST_TEMPLATE.md` 파일이나 `.github/PULL_REQUEST_TEMPLATE/` 폴더가 있으면 **그 파일의 절 이름을 그대로 쓴다.** 이 문서의 절 이름으로 바꾸지 않는다 — 같은 저장소의 PR들이 서로 다른 형태가 되면 나중에 읽을 때 어느 쪽이 기준인지 알 수 없다.

없는 절만 아래에 덧붙인다.

```bash
ls .github/PULL_REQUEST_TEMPLATE.md .github/PULL_REQUEST_TEMPLATE/ 2>/dev/null
```

`.github/PULL_REQUEST_TEMPLATE/` 폴더 안의 파일은 GitHub이 자동으로 채우지 않는다. 그 본문을 쓰려면 PR 생성 주소에 `template` 질의 문자열을 붙여야 한다.

```text
https://github.com/<owner>/<repo>/compare/<base>...<head>?expand=1&template=release.md
```

## PR을 여는 절차

1. 붙일 label을 확인한다 — 아래 「릴리즈 노트가 label로 만들어질 때」를 먼저 읽는다
2. 본문 초안을 대화에 그대로 보여준다
3. 승인받는다
4. 파일로 저장해 `--body-file`로 넘긴다 — 본문에 백틱과 줄바꿈이 있어 `--body`로 넘기면 셸이 깨뜨린다

```bash
gh pr create --base dev --head feature/app-ranking-roblox-수집 \
  --title 'feat(app-ranking): 기간을 주 단위로 선택' \
  --label '✨ Feature' \
  --body-file /tmp/pr-body.md
```

**승인 전에 실행하지 않는다.** `SKILL.md`의 「푸시는 하지 않는다」와 같은 성격이다.

## 릴리즈 노트가 label로 만들어질 때

release-drafter를 쓰는 저장소는 **PR에 붙은 label로 릴리즈 노트의 분류와 다음 버전을 정한다.** label이 없으면 그 PR은 노트에서 빠지고 버전은 기본값에 머문다.

```bash
ls .github/*drafter*.yml 2>/dev/null   # 설정 파일이 있는지
gh label list                          # 그 저장소에 있는 label 이름
```

설정 파일의 `categories` 항목에 적힌 label 이름을 **그대로** 쓴다. 이모지와 띄어쓰기까지 같아야
한다.

커밋 type과 label을 잇는 표는 저장소마다 다르므로 만들어 두지 않는다. 설정 파일을 읽고 그때 고른다.
