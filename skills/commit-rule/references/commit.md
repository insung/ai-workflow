# 커밋 메시지 상세

`SKILL.md`의 제목 규칙에 이어, 본문·푸터와 판단이 갈리는 사례를 정리한다.

## 전체 구조

```text
<type>(<scope>): <요약>
                              ← 빈 줄 1개 (본문이 있을 때 반드시 필요)
<본문>

<푸터>
```

## 본문

본문은 선택이다. **제목만으로 "왜"가 설명되면 쓰지 않는다.** 사소한 수정에 본문을 붙이면 읽는 비용만 늘어난다.

쓸 때는 무엇을 했는지가 아니라 **왜 그렇게 했는지**를 쓴다. 무엇을 했는지는 diff를 보면 알 수 있지만, 왜 그 선택을 했는지는 코드에 남지 않는다.

- 한 줄 72자 근처에서 줄바꿈한다.
- 여러 항목은 `-` 목록으로 쓴다.
- 배경과 문제, 선택한 이유, 감수한 트레이드오프, 영향 범위를 담는다.

```text
fix(app-usage): 일별 집계 재실행 시 중복 적재 차단

기존 INSERT 방식은 배치를 재실행하면 같은 날짜 데이터가 중복 적재되어
사용량 지표가 실제보다 크게 표시됐다.

- (date, app_id) 유니크 키 기준 upsert로 변경
- 이미 쌓인 중복 행은 마이그레이션에서 정리
- 재실행이 잦은 크롤링 배치 전반에 같은 방식을 적용할 예정
```

## 푸터

```text
BREAKING CHANGE: 순위 응답의 rank 필드가 문자열에서 정수로 변경
Refs: #12
```

`BREAKING CHANGE:`를 쓸 때는 제목의 type 뒤에도 `!`를 붙인다.

```text
feat(app-ranking)!: 순위 응답의 rank를 정수로 반환

BREAKING CHANGE: 순위 응답의 rank 필드가 문자열에서 정수로 변경
```

## 요약에서 자주 틀리는 지점

### type과 뜻이 겹치는 동사

`feat`는 추가, `fix`는 수정을 이미 뜻한다. 요약을 그 동사로 끝내면 같은 정보가 두 번 들어간다.

```text
❌ feat(search): 지표 자동완성 추가
✅ feat(search): 지표명 입력 시 자동완성 제안

❌ fix(navigation): 앱 선택 유지되도록 수정
✅ fix(navigation): 화면 이동 후에도 선택한 앱 유지
```

다만 **동사가 기능 자체를 가리키는 경우는 예외**다. 아래는 "내가 변경했다"가 아니라 "사용자가 변경할 수 있다"는 뜻이므로 올바르다.

```text
✅ feat(dashboard): 위젯을 드래그해 순서 변경
```

요약이 이런 동사로 끝날 때는 "내가 무엇을 했다"인지 "사용자가 무엇을 할 수 있다"인지로 구별한다. 앞이면 고치고, 뒤면 그대로 둔다.

### scope를 레이어로 쓰는 경우

```text
❌ feat(backend): 순위 집계 API
❌ feat(frontend): 대시보드 화면
✅ feat(app-ranking): 기간별 순위 집계 조회
✅ feat(dashboard): 위젯 배치 화면
```

프런트엔드와 백엔드 커밋이 같은 기능 scope로 묶여야 릴리즈 노트가 기능 단위로 읽힌다. 레이어를 scope로 쓰면 그 연결이 끊긴다.

### scope가 모호한 경우

읽는 사람이 scope만 보고 "무엇에 관한 변경인지" 떠올릴 수 없으면 너무 넓은 단어다.

```text
❌ feat(document): 프로젝트 자료를 문서 허브로 정리하는 스킬   ← 어떤 문서? 무슨 문서 작업?
✅ feat(document-hub): 프로젝트 자료를 문서 허브로 정리하는 스킬

❌ fix(data): 일별 집계 중복 적재 차단                    ← 어떤 데이터?
✅ fix(app-usage): 일별 집계 중복 적재 차단
```

반대로 지나치게 쪼개도 릴리즈 노트가 파편화된다. `app-ranking-crawler`와 `app-ranking-api`로 나누면 같은 기능이 두 곳에 흩어진다. **사용자에게 하나의 기능으로 보이는 단위**가 적절한 크기다.

### 한 커밋에 여러 주제

scope를 하나 고를 수 없다면 커밋을 나눠야 한다는 신호다. `git add -p`로 분리한다.

### 같은 주제인데 표기가 갈리는 경우

`auth`와 `authentication`, `app-ranking`과 `ranking`이 섞이면 릴리즈 노트에서 같은 주제가 두 곳에 나뉜다. scope는 목록으로 강제하지 않으므로, 새 커밋을 쓰기 전에 최근 기록에서 이미 쓴 표기를 확인한다.

```bash
git log --pretty=%s | head -30
```

표기가 실제로 갈리기 시작하면 그때 `commitlint`의 `scope-enum`으로 고정하는 것을 검토한다. 아직 일어나지 않은 문제에 미리 목록을 만들면 주제가 늘 때마다 설정을 고쳐야 한다.

### 저장소 유형별 scope 예시

실제 scope는 `git log --pretty=%s | head -30`으로 먼저 확인한다. 아래는 새 주제를 만들 때의 참고다.

- AI 작업 시스템 저장소: 시스템 구성 요소 (`workflow`, `automation`, `skill-discovery`)
- 제품 저장소: 도메인 기능명 (`app-ranking`, `dashboard`, `search`, `report`)
- 문서 저장소: 문서가 다루는 주제명 (`operations`, `handbook`, `domain-knowledge`)

### 개수만 적은 요약

수만 적으면 나중에 읽는 사람은 무엇을 세었는지 알 수 없다. 무엇을 고쳤는지를 쓰고, 수는 본문에 적는다.

| 고치기 전 | 고친 뒤 |
| --- | --- |
| 이름 없이 가리키는 말을 기계가 잡게 한다 | 이름 없이 가리키는 말을 잡는 검사와 훅 |
| 두 음절 수 관형사도 잡는다 | 「열두 곳」 같은 두 음절 수 관형사도 검출 |
| 이름 없이 가리키던 11곳에 이름을 넣는다 | 시트 칸과 원천을 개수 대신 이름으로 표기 |

### 사람 이름이 들어간 요약

누가 요청했고 누가 답을 기다리는지는 문서에 적고, 커밋에는 역할이나 사건으로 쓴다.

```text
✅ docs(ai-insight): 공유한 제안 메시지와 전달 범위
✅ fix(app-ranking): 요청자가 지적한 중복 집계 제거
✅ feat(dashboard): 기획 회신에 따라 기간 선택을 주 단위로

❌ docs(ai-insight): ○○님에게 공유한 제안 메시지        ← 제목에 이름
❌ fix(app-ranking): ○○님이 잘못 넣은 필터 수정          ← 개인과 실수를 묶는다
```

### 여러 지점이 한꺼번에 틀린 예

```text
✅ feat(app-ranking): Roblox 게임 순위를 수집 대상에 포함
✅ fix(app-ranking): 앱 ID 누락 시 500 대신 404 응답
✅ feat(dashboard): 위젯을 드래그해 순서 변경

❌ feat(backend): Roblox 게임 순위 수집 추가      ← scope가 레이어, 요약이 중복
❌ fix: 404 반환하도록 수정                       ← scope 없음, 요약이 중복
```

## 릴리즈 노트에 실리는 기준

`feat`, `fix`, `perf`와 `BREAKING CHANGE`만 릴리즈 노트에 실린다. 나머지 type은 히스토리에는 남지만 노트에서 제외된다.

노트를 만들 때는 `git log --first-parent`를 쓴다. 머지 커밋만 나오므로 feature 브랜치 내부의 세부 커밋이 섞이지 않는다.

```bash
git log --first-parent --pretty=format:'%s' backend-v1.1.0..backend-v1.2.0
```
