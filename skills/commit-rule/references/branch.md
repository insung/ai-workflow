# 브랜치와 배포 상세

`SKILL.md`의 브랜치와 머지 규칙을 저장소의 실제 운영 방식에 적용할 때 읽는다.

## 기존 체계를 먼저 확인한다

```bash
git branch -a
git log --all --decorate --oneline -30
git tag --sort=-creatordate | head -10
```

로컬 원격 참조는 마지막 fetch 이후 상태일 수 있다. 최신 원격 상태가 결정에 중요하면 네트워크 작업 전에 사용자 요청 범위와 인증 상태를 확인한다.

| 보이는 모습 | 기본 판단 |
| --- | --- |
| `main` 하나 | `main`을 기본 브랜치로 사용 |
| `dev`·`main` 또는 `develop`·`main` | 앞 단계 브랜치에서 작업하고 그 브랜치로 PR |
| `master`·`develop`·`release/*` | 기존 git-flow 유지 |

이름만으로 통합·배포 브랜치를 판정할 수 없으면 workflow와 저장소 문서를 확인한다. 그래도 불명확하면 사용자에게 묻고 브랜치를 만들거나 머지하지 않는다.

## 배포하지 않는 저장소

문서, 지식베이스, 개인 스킬 저장소는 기본 브랜치 하나를 사용한다. 기능별 장기 브랜치, 배포 브랜치와 환경별 브랜치를 만들지 않는다. 사용자가 별도 리뷰 흐름을 요청한 경우에만 짧게 유지되는 작업 브랜치를 사용한다.

## 배포 저장소

### 작업 브랜치

기존 접두사를 우선한다. 새 저장소는 다음을 기본으로 한다.

```text
feature/<scope>-<짧은-설명>
fix/<scope>-<짧은-설명>
hotfix/<scope>-<짧은-설명>
```

- 기본·통합 브랜치에서 분기한다.
- 하나의 배포 가능한 주제만 담는다.
- 작업이 끝난 뒤 PR로 기본·통합 브랜치에 반영한다.
- 머지된 원격 작업 브랜치는 저장소 설정의 자동 삭제를 사용할 수 있다.

### rebase와 merge

- `wip`, 오타, 포맷처럼 독립된 판단이 없는 잔커밋은 PR 전에 작업 브랜치에서 정리한다.
- 다른 사람이 함께 쓰는 작업 브랜치는 동의 없이 rebase하지 않는다.
- 기본·통합·배포 브랜치는 rebase하거나 force push하지 않는다.
- 작업 브랜치에 force push가 꼭 필요하면 `--force-with-lease`를 사용한다.
- 저장소에 기존 merge 정책이 있으면 따른다.
- 정책이 없고 개별 커밋의 판단을 보존해야 하면 `--no-ff` merge를 사용한다.
- squash가 판단 이력을 없애는지 애매하면 사용자에게 확인한다.

히스토리를 기능 단위로 볼 때는 다음을 사용한다.

```bash
git log --first-parent <기본-또는-통합-브랜치>
```

## 새 저장소 기본안

처음에는 `main` 하나와 짧게 유지되는 작업 브랜치로 시작한다. `dev`, `qa`, `prod` 같은 장기 브랜치는 실제 환경별 배포 흐름이 확인될 때만 추가한다. 이미 운영 중인 저장소를 이 기본안으로 임의 전환하지 않는다.

## 태그와 배포

태그 형식과 배포 트리거는 저장소마다 다르다. workflow, 배포 문서와 최근 태그를 확인한 뒤 기존 형식을 따른다.

태그 전에 확인할 것:

1. 대상 커밋이 필요한 환경에서 검증되었는가
2. 이전 태그 이후 변경을 설명할 수 있는가
3. 태그가 실제로 어떤 배포를 일으키는가
4. 되돌릴 이전 배포 지점을 알고 있는가

버전 증가는 저장소 정책이 없을 때만 Conventional Commits를 참고한다. `BREAKING CHANGE`는 major, `feat`는 minor, `fix`와 `perf`는 patch 후보다.

## hotfix

긴급 수정은 현재 배포된 태그나 배포 브랜치에서 분기한다. 수정 배포 뒤 기본·통합 브랜치에도 같은 변경을 반영한다. 이를 빠뜨리면 다음 정규 배포에서 긴급 수정이 사라질 수 있다.
