# Career Achievement Capture

업무 중 떠오른 성과를 잃지 않게 짧게 기록하고, 나중에 이력서나 면접에서 검증 가능한 주장으로 바꿀 재료를 모은다. 기록의 양보다 사용자의 기여, 실제 변화와 증거를 구분하는 것이 중요하다.

## 정본 찾기

1. 사용자가 허브를 지정하지 않았으면 현재 작업공간과 형제 디렉터리에서 `my-document-hub`를 찾는다. 하나만 확인되면 사용하고, 없거나 둘 이상이면 사용자에게 묻는다.
2. 허브와 현재 작업 저장소의 `AGENTS.md`, 허브의 `my-profile/README.md`, `008-career-achievement-inbox.md`, `007-evidence-ledger.md`, `009-career-opportunity-review.md`를 존재하는 범위에서 읽는다.
3. 빠른 기록은 inbox, 수치와 근거가 갖춰진 주장은 ledger가 정본이다. 지원처별 자기소개나 공개 문서를 자동으로 만들지 않는다.

## 요청을 처리하는 방식

다음 표현은 현재 대화에서 성과 후보를 찾아 inbox에 기록해 달라는 명시적 요청으로 취급한다.

- `나는 <목적>을 하기 위해 대화를 시작했다. 내 생각에는 나의 성과는 <변화>다.`
- `작업하던 이것을 <성과>로 만들어줘.`
- `이 내용을 성과로 기록해줘.`
- `나중에 수치화할 자료로 남겨줘.`

사용자가 저장이나 기록을 요청하지 않고 성과가 될 수 있는지만 물으면 후보와 부족한 근거만 답하고 파일을 수정하지 않는다.

## 현재 대화에서 먼저 채우기

사용자에게 다시 묻기 전에 현재 대화, 실행 결과와 접근 가능한 작업 산출물에서 다음을 찾는다.

- 대화를 시작한 목적과 해결하려던 문제
- 변경 전 상태나 기준선
- 사용자가 선택·결정·구현·조율한 부분
- 코드, 테스트, 로그, 지표 또는 피드백으로 확인된 변화
- 성과를 보여 주는 기술·운영·사업·조직 영향의 종류
- 사용자의 직접 진술, AI의 해석, 실제 실행 결과의 구분

AI가 대신 구현한 경우에도 사용자가 소유한 문제 정의, 범위 결정, 판단 기준과 검증 설계는 기여로 기록할 수 있다. AI가 실행했다는 사실을 사용자가 직접 구현한 것으로 바꾸지 않는다.

## 즉시 기록의 최소 조건

inbox 기록에는 다음 세 가지가 필요하다.

1. 무엇을 바꾸려 했는가
2. 사용자가 무엇을 결정하거나 기여했는가
3. 무엇이 달라졌거나 달라졌다고 판단하는가

현재 대화에서 세 항목을 합리적으로 복원할 수 있으면 바로 기록한다. 핵심 항목이 없으면 사용자만 답할 수 있는 질문을 한 번에 하나만 한다. 질문 우선순위는 `확인된 변화 → 사용자의 기여 → 업무 목적`이다. 정확한 날짜나 수치가 아직 없다는 이유로 기록을 막지 않고 `확인 필요`로 남긴 뒤, 다음에 확인할 근거 하나를 완료 보고에 제시한다.

## 과거 성과를 회상해 기록할 때

- `기록 시점`은 inbox에 적은 현재 날짜이고, `성과 발생 시기`는 실제 업무가 있었던 시기다. `CAP` ID에는 기록 시점을 사용한다.
- 발생 시기는 확인 가능한 정밀도만큼 `YYYY-MM-DD`, `YYYY-MM`, `YYYY`, `YYYY~YYYY`, `재직 기간 중·세부 시기 미상`으로 적는다. 정확한 날짜를 추정해 만들지 않는다.
- 사용자의 기억만 근거인 내용은 `recalled`로 기록한다. 당시 문서·이슈·코드나 동료 확인을 찾으면 근거 수준을 다시 판정한다.
- 기억에 의존한 수치는 `약`, 범위 또는 대략적인 규모로 보존한다. 정밀한 기준값이 없는 수치에서 정확한 변화율을 계산하지 않는다.
- 발생 시기는 다른 경력과의 선후관계, 최신성 또는 기여 귀속을 판단할 때만 후속 질문으로 우선한다. 그렇지 않으면 시기 미상으로도 수집을 계속한다.

## 성과 근거 필드

정량 지표는 성과의 크기를 설명하지만 그 자체로 사용자의 기여를 증명하지 않는다. 수치와 비정량 근거를 함께 보고 현재 확인된 것만 기록한다.

### 정량 근거

| 필드 | 판단 기준 |
| --- | --- |
| 지표 | 시간, 비용, 오류, 장애, 처리량, 정확도, 전환, 매출, 재작업, 문의 등 변화의 단위 |
| 측정 정의 | 무엇을 세었는지, 비율이면 분자·분모가 무엇인지 |
| 기준값 | 변경 전 값 또는 비교군. 없으면 언제 어디서 확인할지 기록 |
| 결과값 | 변경 후 같은 정의로 측정한 값 |
| 변화량 | 절대값과 비율 중 오해가 적은 방식. 계산 근거를 함께 보존 |
| 기간 | 측정 시작·종료일 또는 비교 기간 |
| 범위 | 사용자, 요청, 데이터, 서버, 고객, 팀 등 지표가 적용된 모집단 |
| 값 형태 | 정확한 값, 근사값, 범위 또는 확인 불가 |
| 증거 | 대시보드, 이슈, PR, commit, 로그, 테스트, 회고, 검토자 등 다시 확인할 위치 |
| 다른 원인 | 트래픽 변화, 다른 팀 작업, 정책 변경처럼 결과에 영향을 준 요인 |

지표의 전후 정의나 기간이 다르면 직접 비교하지 않는다. 코드 줄 수, 문서 수, 테스트 통과만으로 비즈니스·운영 성과를 주장하지 않는다.

### 비정량 근거

수치가 없더라도 다음 변화는 성과 후보의 강도를 설명할 수 있다.

- 담당한 시스템·고객·데이터·협업 팀의 범위와 업무 중요도
- 임시 대응이 아니라 이후에도 사용된 구조·정책·도구인지와 지속 기간
- 발생한 장애 감소가 아니라도 탐지·격리·복구·재발 방지 장치를 만든 사실
- 여러 팀의 결정을 정렬하거나 표준으로 채택되게 한 영향
- 고객·운영자·동료의 확인 가능한 피드백과 후속 사용

숫자가 없는 결과를 `measured`로 부르지 않는다. 대신 확인 가능한 범위에서 `recalled`, `observed`, `validated`로 관리하고, 피한 장애나 비용을 실제 절감액처럼 계산하지 않는다.

## 기록과 승격

- `008-career-achievement-inbox.md`의 템플릿을 사용해 `CAP-YYYYMMDD-NN`을 부여한다. 같은 날짜의 마지막 번호를 확인하고 중복되지 않게 한다.
- 첫 항목을 기록할 때 `아직 기록된 항목이 없다.` 문구를 새 항목으로 교체한다.
- 같은 대화와 같은 결과를 가리키는 기존 항목이 있으면 새 항목을 만들지 않고 확인된 필드만 보완한다.
- 대화 전문이나 로그 전체를 복사하지 않고, 성과 판단에 필요한 요약과 다시 찾을 수 있는 위치만 남긴다.
- 정량 성과는 측정 정의·기준값·결과값·단위·기간·범위와 증거가 갖춰지면 `measured` 승격 후보로 보고한다. 비정량 성과는 범위·변화·기여와 확인 근거가 분명하면 `observed` 또는 `validated` 승격 후보가 될 수 있다.
- 사용자가 ledger 반영을 요청하면 기존 `CLM-NNN`을 보완하거나 새 항목을 만들고 inbox의 `ledger 연결`을 갱신한다. 원래 기록은 삭제하지 않는다.
- `recalled`, `observed`, `measured`, `validated` 상태는 ledger의 정의를 따른다. 사용자 진술만 있는 결과를 독립적으로 검증된 결과처럼 승격하지 않는다.

## 수집 현황을 정리할 때

사용자가 지금까지 모은 성과를 검토·수치화·이력서 재료로 정리해 달라고 하면 inbox와 ledger를 함께 읽는다.

- 중복 후보, ledger 승격 가능 항목, 수치 확인이 필요한 항목을 구분한다.
- `사업·제품 영향`, `안정성·품질`, `속도·비용`, `규모·복잡도`, `리더십·조직 영향` 중 어떤 증거가 쌓였는지와 비어 있는지를 보여 준다.
- 모든 빈칸을 한꺼번에 질문하지 않고, 경력 주장에 가장 큰 영향을 주는 다음 질문 하나만 고른다.
- 지원처가 정해졌다면 해당 역할의 요구사항과 연결하되, 원래 기록과 증거 수준을 바꾸지 않는다.

### 시각화 규칙

- 근거 현황은 성과 유형별 `recalled`, `observed`, `measured`, `validated` 항목 수를 함께 보여 준다. 서로 다른 근거 수준을 임의의 종합 점수로 합치지 않는다.
- 전후 차트는 측정 정의·기간·범위가 비교 가능한 항목만 사용하고, 원값·절대 변화·변화율·단위·값 형태와 연결된 `CLM`을 표시한다.
- 누락 값은 0으로 바꾸지 않고 `확인 불가`로 표시한다. 회상 수치는 정확한 값과 같은 막대나 선으로 오해되지 않게 근사 또는 범위임을 드러낸다.
- 자료가 적으면 빈 차트를 만들지 않고 표와 부족한 근거를 보여 준다. 충분한 자료가 생기면 사용자가 요청한 형식에 맞춰 표, 차트 또는 별도 시각 자료를 만든다.

## 다음 회사와 역할을 검토할 때

수집 자료를 [경력 증거 대시보드와 이직 검토](../../../my-document-hub/my-profile/009-career-opportunity-review.md)의 판정 규칙에 맞춰 읽는다.

1. 대상 회사·역할·레벨과 공고 원문 또는 출처·확인일을 확보한다. 현재 채용 정보와 회사 사실은 검토 시점에 다시 확인한다.
2. 필수 요건과 핵심 책임을 각각 `direct`, `adjacent`, `missing`, `unknown`으로 분류하고 관련 `CLM`을 연결한다.
3. 사용자의 직접 경력, 추론, 외부에서 확인한 현재 사실을 구분한다. `recalled`만 있는 항목은 `direct`로 판정하지 않는다.
4. 회사 이름의 인지도나 기술 키워드 수로 점수를 만들지 않는다. 역할 적합성, 증거 강도, 사용자의 필수 조건과 정보 부족을 분리한다.
5. 결론은 `지원 우선`, `조건부 지원`, `보류`, `판단 불가` 중 하나와 핵심 이유, 가장 가치 있는 다음 행동 하나로 낸다.

사용자가 기록을 요청하면 `009-career-opportunity-review.md`의 검토 기록에 `REV-YYYYMMDD-NN`을 추가한다. 단순히 추천이나 검토만 요청했다면 파일을 수정하지 않고 같은 형식으로 답한다.

## 기밀과 공개 경계

성과 기록은 기본 비공개다. 회사명, 고객명, 내부 제품명, 내부 URL, 접근 정보, 소스 코드, 원문 로그, 미공개 매출·트래픽 수치를 개인 허브에 그대로 복사하지 않는다.

- 식별자는 역할이나 범주로 익명화한다.
- 비공개 수치는 허용되는 경우 비율·범위로 기록하고, 원본 증거가 있는 내부 위치만 사용자가 다시 찾을 수 있는 수준으로 남긴다.
- 공개 가능 여부가 확인되지 않으면 `private`로 둔다.
- 이력서·GitHub·블로그용 표현은 대상과 공개 범위를 사용자가 승인한 뒤 별도로 추출한다.
- 성과를 기록하기 위해 현재 회사 저장소나 외부 시스템을 수정하지 않는다.
